# HK1 RBOX X4 客厅壁挂信息屏：实机检查与实施方案

> 状态：**设计/待实机验证** · 更新日期：2026-11-08  
> 适用目标：一台主机连接 20–24 英寸 HDMI 显示器，平时显示时钟、天气、BOLOLO 喂养摘要、Home Assistant 状态；需要时支持 iPhone 投屏和电视/影片播放，并可设置闹钟。  
> 当前策略：**优先保留 HK1 盒子的原生 Android，避免先刷 Linux**。本文只记录待验证的能力，不代表已完成部署。

## 0. 结论与现有环境

- 用户已有：树莓派 3B/3B+、疑似 HK1 RBOX X4 的电视盒子、运行 Home Assistant 和 BOLOLO 服务的 OpenWrt；计划购买 20–24 英寸壁挂显示器。
- 已收到的图片是 HK1 RBOX S905X4 系列**商品宣传图**，不是实机「关于设备」或拆机信息。**不能据此认定实际 SoC、RAM、主板、Android 固件和接口配置。**
- 现有 BOLOLO 仓库以 Python/SQLite 实现家庭喂养网页，可由 OpenWrt 持续运行；客户端通常访问 `http://<OPENWRT_LAN_IP>:8765/`。其中 `/clock` 是**计划新增**的专用大屏页面，不是当前已实现接口。
- 优先路线：HK1 作为唯一 HDMI 主机，Android 浏览器显示信息屏，投屏接收器与播放器以 Android 应用切换；OpenWrt 继续作为家庭数据服务。
- 备选路线：树莓派 3B/3B+ + Raspberry Pi OS 用于定制 Linux 信息屏，优点是自由度与可靠定时服务，缺点是 1GB 内存及现代视频解码/投屏性能有限。
- 不建议未经匹配实机硬件/设备树及启动链验证，就将社区 Linux 镜像写入盒子的 eMMC。

## 1. 实机检查清单（优先完成）

### A. 硬件与固件

- [ ] 核对机身底部标签、型号（HK1 RBOX X4 / X4S / 其他）、包装标注；必要时拍主板编号（不公开序列号）。
- [ ] 核对 SoC 实际型号（S905X4 还是其他），记录证据来源。
- [ ] 确认可用 RAM（2GB / 4GB 等）、存储总量及剩余空间。
- [ ] 确认 Android 系统版本、API 级别、固件/构建版本。
- [ ] 确认 Wi-Fi/蓝牙是否可用，是否有有线以太网。
- [ ] 确认 HDMI 输出分辨率、刷新率，HDMI 音频或其他音频输出可用。
- [ ] 确认遥控器操作、USB 接口、断电重启及开机恢复行为。
- [ ] 记录屏幕型号、分辨率、VESA 孔位、待机功耗与唤醒行为。

可以安装 AIDA64 或 Device Info HW，优先截图：**系统 / SoC(CPU) / 内存**三个页面。系统应用可能对 SoC 名称识别错误，互相核对 `getprop`，必要时读取主板丝印。

如果已经启用开发者选项及 ADB，可在可信局域网内连接后只执行**只读命令**：

```sh
adb devices
adb shell getprop ro.product.model
adb shell getprop ro.product.board
adb shell getprop ro.hardware
adb shell getprop ro.soc.model
adb shell getprop ro.build.version.release
adb shell getprop ro.build.version.sdk
adb shell cat /proc/meminfo
adb shell df -h /data
```

不要将完整设备序列号、MAC、账号、Token、个人局域网信息或未经脱敏的系统日志提交 GitHub。公开分享截图前先遮盖可识别信息。不要在不可信网络开放 ADB。

### B. 功能冒烟测试

- [ ] 在 HK1 浏览器打开 BOLOLO 当前页面（先使用 `/` 而非尚不存在的 `/clock`）。
- [ ] 浏览器能够打开 HA 仪表盘，并能在遥控器下正常使用。
- [ ] iPhone 与盒子在可互通的网络中；测试 AirPlay 接收应用是否可发现、建立连接、稳定退出。
- [ ] 分别验证屏幕镜像、普通视频、音频；受 DRM 保护的应用可能无法镜像。
- [ ] 测试视频播放器的 1080P 流畅度、音画同步和遥控器控制。
- [ ] 测试 Android 应用的开机自启、返回主页、重启后恢复。
- [ ] **实测**闹钟在前台、后台、显示器待机、盒子休眠/重启后能否响铃。
- [ ] 测试显示器纯黑页面是否仍有背光漏光，以及断开/恢复 HDMI 信号后的待机与唤醒。
- [ ] 验证长时间运行（例如连续一昼夜）无内存异常、浏览器假死和网络掉线。

## 2. 推荐部署架构

```text
iPhone  ───── AirPlay / 投屏接收应用 ───┐
                                       │
OpenWrt ─── BOLOLO HTTP / HA HTTP ─── HK1 RBOX X4 (Android)
                                       │ HDMI
播放器（Kodi / 其他 Android 应用）────┘
                                       │
                               20–24 寸壁挂显示器
```

**职责划分**

1. **OpenWrt**：保留 BOLOLO Python + SQLite、MQTT 监听和 HA，负责数据落盘与自动备份。
2. **HK1 Android**：只负责 UI、浏览器、投屏接收、影视播放和遥控器；尽量不把家庭核心数据存进盒子。
3. **显示器**：单 HDMI 输入，优先 20–24 寸 1080P、支持 VESA 壁挂、可控制亮度/待机。长时间显示静态时钟时考虑像素位置微调或定时熄屏。

**不建议两台主机通过 HDMI 切换器反复切换**，因为用户偏好一个主机完成显示与影音。

## 3. Android 侧分阶段部署

### 第一阶段：能稳定显示

1. 先保留厂商 Android 固件，检查系统时间/NTP、Wi-Fi 或有线网络。
2. 安装可在此盒子上使用的浏览器；尝试 Fully Kiosk Browser（须验证对该固件与遥控器的兼容）。
3. 起始页先指向 `http://<OPENWRT_LAN_IP>:8765/`；当本仓库实现 `/clock` 后再切换。
4. 逐项测试自启动、浏览器全屏、页面重连、遥控器返回/主页键和异常恢复。
5. 不要开启阻止切换至投屏/影音应用的 Kiosk 锁定模式。

### 第二阶段：投屏与影音

1. 选择一款能在此盒子上工作的 AirPlay 接收器（例如 Sideplay / AirScreen，**不预设已兼容**）。
2. 测试 iPhone 发现盒子、连接、停止投屏、重复连接；验证是否可以自动将接收界面带到前台。
3. 安装 Kodi 或用户已有播放器；测试实际媒体格式、声音输出与遥控操作。
4. **投屏停止后自动回到时钟不是已验证的现成功能**：如无原生支持，再研究启动器/自动化/ADB 回调方案，避免强杀后台应用。

### 第三阶段：闹钟与熄屏

1. 闹钟应有**独立于当前网页前台**的调度机制；Android TV 盒子的后台、休眠、系统闹钟能力必须实机验证。
2. 如果本地 Android 闹钟可靠性不达标：让 OpenWrt/HA 负责调度，并通过经过实测能响铃的音箱/通知设备输出，HK1 仅展示闹钟信息。
3. 夜间优先让**显示器真正待机/关背光**，而不是仅显示纯黑网页（LCD 仍可能亮背光）。
4. 显示器待机、HDMI CEC、厂商 HDMI 控制及定时开关功能都需要分别测试；不可假定所有显示器支持 HDMI-CEC 或 Android 自动亮屏。
5. 对闹钟和提醒验证断网、重启、音频焦点被 Kodi/投屏占用的情况。

### 第四阶段：远程管理

- 首选局域网 ADB（按需开启）、浏览器管理及 OpenWrt/HA 侧的可观测接口。
- 如果使用 Fully Kiosk Remote Admin：设置独立强密码，只监听家庭网络，**禁止公网端口转发**。
- 记录盒子内存占用、应用意外退出、当前页面及开机自启状态；避免持续收集敏感日志。
- 系统维护前备份必要的应用配置；BOLOLO 数据仍由 OpenWrt 负责备份。

## 4. BOLOLO 仓库后续开发（供 Codex）

**原则：改动保持小而清晰；不要把整个服务迁移到 Android。开发按现有 AGENTS.md 直接提交 `main`，不创建 PR。**

### M1：新增只读大屏页面 `/clock`

- [ ] 新增深色壁挂页面，大字号显示时间/日期，适配 20–24 寸 1080P。
- [ ] 复用已有 `/api/feeds`、`/api/p50` 和 `/api/trend`，显示最近喂奶、今日合计、设备状态与监听新鲜度。
- [ ] 加载失败时显示上次更新时间，不将离线缓存冒充实时数据。
- [ ] 支持遥控器方向键与返回键，优先只读展示。
- [ ] 未完成 `/clock` 前不要在部署文档中把它写作已存在接口。

### M2：HA 摘要

- [ ] 先核实 HA 提供数据的最小途径，优先 OpenWrt 本地只读代理或经过授权的聚合摘要。
- [ ] 不在前端 JS / HTML 里写入 HA 长期访问令牌。
- [ ] 可选的天气、室内温湿度、场景状态，应允许用户关闭；缺失时页面仍可用。

### M3：可靠性与自动化

- [ ] 为喂奶自动事件与实际摄入统计明确区分「备奶」和「已确认喂养」。
- [ ] 为信息屏加入网络断开、重新连接和后端不可用的状态提示。
- [ ] 增加轻量测试及部署说明；闹钟的响铃保障不依赖 `setInterval` 的网页计时。

## 5. 是否刷 Linux？决策门槛

- **当前首选：Android**。它更有机会在一台 S905X4 盒子上兼顾常见影音应用和 AirPlay 接收。
- **CoreELEC**：适合 Kodi 影音中心，但不应默认具备完整 Chromium 桌面、网页 Kiosk、Android 投屏接收应用。
- **社区 Debian/Armbian**：适合 SSH/Python/systemd DIY，但必须按**具体主板 + DTB + 引导方式**验证 HDMI、GPU、VPU 硬解、Wi-Fi、音频、遥控器等；同芯片不代表同一盒子可用。
- 如决定实验 Linux：优先有明确适配记录的外部存储启动，保留原 Android 恢复办法；**未实测前不改写 eMMC / Bootloader**。

### 切换为 Linux 的最低验收标准

- [ ] 能稳定启动和 SSH 登录
- [ ] HDMI 1080P 稳定、网页 Kiosk 可用
- [ ] 网络、音频、USB/遥控器正常
- [ ] Kodi/视频播放满足实际格式需求
- [ ] iPhone 投屏在实际网络上测试成功
- [ ] 自动开机、定时熄屏、闹钟响铃、断电恢复通过测试

若不能同时满足，保留 Android，树莓派 3B/3B+ 作为备用 Linux DIY 设备。

## 6. 验收标准

| 场景 | 验收 |
| --- | --- |
| 开机 | 无须人工操作即可进入时钟 / 信息屏 |
| BOLOLO | 能显示喂养摘要，断网时提示数据已过期 |
| HA | 展示选定状态，不暴露访问凭据 |
| 投屏 | iPhone 可发现接收器、连接、停止并重复使用 |
| 影视 | 遥控器可打开播放器，声音正常 |
| 恢复时钟 | 影音退出后可用遥控器直接恢复；自动恢复需额外验证 |
| 闹钟 | 前台、后台、屏幕待机及重启情况逐项验证，确保有可靠声音输出 |
| 省电 | 定时进入实际低功耗待机，非仅黑屏 |
| 远程维护 | 局域网访问受保护，服务日志不包含密钥/账号等敏感信息 |

## 7. 下一步需要用户提供的最少信息

1. HK1 实机「关于设备 / 系统 / CPU / 内存」截图（先脱敏）。
2. 盒子是否有声音、遥控器、Wi-Fi/网线，是否能安装 APK。
3. 最终选定的显示器是否有扬声器、VESA 壁挂孔以及 HDMI 待机功能。

收齐这些证据后，再确定 Android 应用安装与启动策略，最后决定是否有必要测试 Linux。
